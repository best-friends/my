# ADR-0003: パスと規約の対応表 context-map を、コードを増やすエージェントが保守する

- Status: Accepted
- Date: 2026-10-22
- Deciders: @rosylilly
- Issue: なし

## Context（背景・課題）

変更する場所が決まっても、その場所に効く規約がどの文書のどの節にあるかは、文書を読まないと分からない。
たとえば `docs/architecture/web-client.md` は約 9 万トークン、`data-model.md` は約 9.4 万トークンあり、全体を読むと 1 タスクの予算を使い切る。
パスから節を引ける表があれば `ctx` が必要な節だけを渡せるが、表が古くなれば誤った前提を渡すことになる。
決定者の指示（原文）:

> 人が管理するというかコーディングエージェントがディレクトリやコードを増やした時に保守される対象であってほしいです

## Decision Drivers（判断基準）

- 新しいディレクトリやモジュールを足した変更が、対応表の更新を忘れられないこと
- 文書の見出しが変わったときに、壊れた参照が残らないこと
- 要約を置かず原文の節を指すこと（要約は古くなる）

## Considered Options（選択肢）

1. 人が保守する表
2. エージェントが保守し、CI が網羅と参照を検査する表
3. 表を置かず、パスと文書の対応を推測する

## Decision（決定）

選択肢 2。

- 表は `tools/agentkit/context-map.yaml`。項目ごとにパスのパターン（`*` は 1 階層、`**` は任意の階層）、読む文書の節（`<path>#<anchor>`）、`make check` のコンテキスト、並行作業で同時に触らない共有ファイルか（本体の workflow.md §9）、短い注意書きを持つ
- `agentkit map check`（`make agentkit-check`、CI）は次のときに失敗する
  - 追跡しているファイルが、どの項目にも `ignore` にも当たらない
  - `strict` のパターン（`internal/app/*`、`app/web/src/features/*` など）に当たるディレクトリを、名前で挙げる項目がない（広いパターンでは足りず、新しいモジュールや画面には専用の項目が要る）
  - 文書の参照が、存在しないファイルや見出しを指している
  - 存在しないチェックのコンテキストを挙げている
- どのパスの変更でも `agentkit` コンテキストを選ぶ（`scripts/changed-contexts.sh`）。ファイルの追加も見出しの変更も、その PR の CI で検出される
- ディレクトリ、モジュール、adapter、画面を足すエージェントは、同じ変更で項目を足すか広げる。項目に挙げる節は、その場所を変える前に読むべき節に絞る

## Consequences（影響）

- 新しい領域を足す PR は context-map.yaml も変えるので、並行作業ではこのファイルが衝突しやすい。項目は独立した行で書き、衝突は両方を残して解消する
- 文書の見出しの名前を変えると、対応表も直す必要がある
