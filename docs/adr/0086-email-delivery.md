# ADR-0086: メール送信のジョブ化・テンプレート・配信停止

- Status: Proposed
- Date: 2026-10-23
- Deciders: @rosylilly
- Issue: #1025

## Context（背景・課題）

サーバーは次のメールを送る。Mailer ポート（`internal/app/kernel/mailer.go`）と、アダプタ `mail/none`（ログに出す）・`mail/smtp`（STARTTLS 必須）があり、`mail/ses` はパッケージの雛形だけがある。

| メール | 要件 | 送り方 |
| --- | --- | --- |
| メールアドレスの確認・再送 | FR-002 | リクエストの中で、コミットの後に同期で `Mailer.Send` |
| パスワードのリセット | FR-002 | 同上 |
| パスワードの変更・削除の通知 | FR-002 | 同上（失敗はログだけ） |
| モデレーターへの通知 | FR-712 | outbox → ジョブ `JobModeratorEmail`（利用者設定 `email_moderator_notifications`） |
| サポーターの通知（支払いの失敗など） | FR-910–FR-917 | outbox → ジョブ `JobSupporterEmail` |

v0 のリリース（M5）に向けて、次が欠けている。

- **送り方**: 同期の送信は、SMTP が遅い・一時的に落ちているとリクエストが遅れ・失敗し、再送もない。ジョブで送るものも、宛先の恒久的な拒否と一時的な失敗を区別せず、どちらも再試行する
- **内容**: 件名と本文を各ユースケースが個別に組み立てている。共通の外枠（サーバー名・連絡先・設定へのリンク）、`From` の表示名、`Reply-To`、`List-Unsubscribe`（RFC 8058）、`Auto-Submitted`（RFC 3834）がない
- **配信の停止**: 通知のメールを止めるには、ログインして設定画面を開くしかない
- **到達性**: SPF・DKIM・DMARC の運用文書と、バウンス・苦情の扱いがない
- **SES**: AWS のターゲット（M6）の `mail/ses` が未実装

ジョブの規約は ADR-0004（at-least-once・冪等なハンドラ）、トランザクションの規約は ADR-0003（外部 I/O をしない）、ジョブの失敗の見え方は ADR-0064 が決めている。
同じバッチの [ADR-0084](0084-maintenance-mode.md)（メンテナンスモード）・[ADR-0088](0088-service-shutdown-modes.md)（サービスの終了）は、全利用者への告知をメールで送る可能性があり、この ADR の送り方と配信停止の区分に乗る。

## Decision Drivers（判断基準）

1. **秘密を残さない**: 確認・リセットのリンクの秘密を、ジョブのペイロード（SQS・Cloud Tasks ではクラウドに置かれる）・`dead_jobs`・ログに残さない（ADR-0019、ADR-0064 §2）
2. **リクエストを外部 I/O から切り離す**: SMTP の遅延・障害が登録やリセットのリクエストを遅らせない。再送がある（ADR-0003・ADR-0004）
3. **到達性**: 主要なメールボックス事業者の送信者要件（SPF・DKIM・DMARC の整合、通知メールのワンクリック配信停止）を満たせる
4. **運用の少なさ**: 小さなサーバーの運営者が、SMTP の事業者を 1 つ設定するだけで送れる。v0 で受信（DSN・Webhook）の口を増やさない
5. **i18n と既存のカタログ**: ICU のメッセージ（ADR-0009）を使い、`server*` 名前空間の制約（リッチテキストのタグ・日時の引数を使わない）を守る
6. **作る量**: v0 で要るものだけを作る。HTML・バウンスの自動処理は後から足せる形にする

## Considered Options（選択肢）

論点ごとに選択肢を挙げる。

### 1. 送り方

- **1A. すべてのメールを用途ごとのジョブにし、ペイロードは ID だけ、秘密はハンドラが発行する**。
  ハンドラが実行時に宛先・ロケール（ADR-0009 §2）を引き、トークンを発行して、組み立てて送る
- **1B. 汎用の送信ジョブ `mail.send` に、組み立て済みのメッセージを積む**。秘密を含む本文は Sealer（ADR-0019 §6）で封じる
- **1C. 同期の送信を残し、失敗したときだけジョブで再送する**

### 2. 本文の形式

- **2A. v0 はプレーンテキストだけ**（`text/plain; charset=UTF-8`）。共通の外枠をテキストで足す
- **2B. `multipart/alternative` で HTML の版を足す**

### 3. バウンス・苦情

- **3A. v0 は送信時の恒久的な拒否だけを扱い、非同期のバウンス・苦情は送信事業者の抑止リストに任せる**
- **3B. SES の通知（SNS）や DSN を受けて、届かないアドレスを自前で記録し、送信を止める**

### 4. `mail/ses`

- **4A. M6 で SES v2 の API（`SendEmail` の Raw content）で作る**。M5 では SES の SMTP インタフェースを `mail/smtp` で使える
- **4B. 作らない**。SES は SMTP インタフェースだけで使い、`mail = ses` の値を消す

## Decision（決定）

> Proposed の間は「推奨案」として書く。Accepted にするのは人間の Decider のみ。

**推奨案: 1A・2A・3A・4A。** 以下を規約とする。

### 1. 送信はすべてジョブで行う

- リクエスト・ユースケースは `Mailer.Send` を直接呼ばない。メールを送る事実と同じトランザクションで、outbox に用途ごとのジョブを積む（ADR-0004）。
  `Mailer` を呼ぶのはジョブのハンドラだけにする
- **ペイロードは ID と分類だけ**（利用者・メールアドレス・通知の ID、要求の時刻）。宛先のアドレス・本文・秘密は積まない。ハンドラが実行時に、宛先・ロケール・サーバー名を引いて組み立てる。
  ADR-0064 の失敗したジョブの画面にペイロードが出ても個人情報・秘密を含まない
- **秘密はハンドラが発行する**。確認・リセットのジョブは、実行のたびに新しいトークンを発行して（`user_tokens` に hash を INSERT）、コミットしてから送る。
  秘密はメールの本文にだけ現れ、ペイロード・DB・ログには残らない。再試行や重複の実行では、別の有効なリンクを持つメールがもう 1 通届きうるが、どちらのリンクも 1 回だけ使え、期限で失効するので害はない
- **実行時の再確認**: ハンドラは送る前に、まだ送る理由があるかを確かめる（アドレスが未確認のまま主たるアドレスか、通知の権限と設定がまだあるか）。なければ送らずに完了する
- **冪等キー**: ジョブの型と、送る理由になった行の ID（通知の ID、確認の要求の ID）で作る。同じ要求から 2 通のジョブは積まない
- **期限**: 取引のメール（確認・リセット）は要求から一定時間（リセットは 15 分、確認は 1 時間）を過ぎたら、送らずに完了する。古いリセットのメールが遅れて届くのを防ぐ
- **再試行**: ポートのエラーを 2 つに分ける。`kernel.ErrMailRejected`（宛先・内容の恒久的な拒否: SMTP の `RCPT TO` / `DATA` への 5xx、SES の `MessageRejected` など）と、それ以外（接続・タイムアウト・4xx など一時的）。
  恒久的な拒否と `ErrInvalidMail` は `queue.Fail`、一時的な失敗は `queue.Retry`。再試行の方針は、取引のメールが 6 回（30 秒からの指数、合計およそ 15 分）、通知のメールが既定の方針（10 回、合計およそ 4 時間）
- **エラーの文**: ハンドラが返すエラーには、メールアドレス・トークン・本文を入れない（ADR-0064 §2）。ジョブの型・通知の ID・SMTP の応答コードだけを入れる
- 登録の応答は、送信の成否を返さなくなる（「確認のメールを送りました」と表示し、届かなければ再送を求める）。送信の失敗はジョブのダッシュボード（`/admin/jobs`、ADR-0064）で見る

### 2. 組み立て（テンプレートと外枠）

- v0 の本文は **プレーンテキストだけ**。HTML の版は作らない
- 件名・本文は今と同じく `locales/<locale>/server*.json` の ICU メッセージで持ち、生成した型付きアクセサで整形する（ADR-0009）。日時は Go 側で整形した文字列を引数に渡す
- **共通の外枠** を `internal/app/kernel` に置く組み立て器（`MailComposer` 相当）が付ける。ユースケースは「分類・宛先・ロケール・件名・本文」を渡すだけにする:
  - 末尾の署名: サーバーの名前、サーバーの URL、`contact_email`（設定されていれば）、「このメールが届く理由」の 1 文
  - 通知のメールには、設定画面へのリンクと配信停止のリンク（§4）
- `Mailer` ポートの `MailMessage` に、分類（`transactional` / `notification` / `announcement`）・`From` の表示名・`Reply-To`・追加のヘッダ（`List-Unsubscribe` 系だけを許す）を足す。アダプタはヘッダの注入を `ValidateMail` で拒否し続ける
- HTML を足すときは、同じ ICU メッセージから Go の `html/template` で作り（利用者の HTML を埋め込まない）、`<html lang dir>` をロケールから付け、外部の画像を読まず、`color-scheme` で明暗に任せる。これは別の ADR で決める

### 3. ヘッダ

| ヘッダ | 値 |
| --- | --- |
| `From` | `"<サーバー名>" <mail_from>`（RFC 2047 で符号化。サーバー名がなければ host） |
| `Reply-To` | インスタンス設定 `contact_email`。未設定なら付けない（`mail_from` は `noreply@` を想定） |
| `Message-ID` | `<UUIDv7@mail_from のドメイン>`。SES など事業者が付け替える場合はそれに従う |
| `Auto-Submitted` | すべてのメールに `auto-generated`（自動応答のループを防ぐ） |
| `List-Unsubscribe` / `List-Unsubscribe-Post` | **通知（`notification`）と告知（`announcement`）のメールだけ**。`<https://{host}/mail/unsubscribe?token=...>` と `List-Unsubscribe=One-Click` |

確認・リセット・パスワードの変更の通知・支払いの失敗は取引のメールで、配信停止の対象にしない（止めると安全や契約に関わる知らせが届かない）。

### 4. 配信の停止

- 配信停止の区分は、利用者設定のメールの項目と 1 対 1 にする。今の区分は `email_moderator_notifications` だけで、通知のメールを足すときは区分と設定の列を一緒に足す。告知（ADR-0084・ADR-0088）の区分は、そのメールを作るときに設定を足す
- 配信停止の **トークンはメールごとにハンドラが発行する**（`user_tokens` の新しい用途 `email_unsubscribe`、区分を持ち、期限 90 日、hash だけを保存）。秘密の扱いは §1 と同じ
- エンドポイント `/mail/unsubscribe`（authpages、ログイン不要）:
  - `POST`（RFC 8058 のワンクリック。本文 `List-Unsubscribe=One-Click`）: トークンを検証し、その区分の設定を off にして `200` を返す。トークンは期限まで何度使ってもよい（冪等）
  - `GET`: 確認の画面を出し、ボタンで同じ `POST` を送る。リンクを先読みするスキャナーで止まらないよう、`GET` では変更しない
- 設定の変更は今の設定の更新と同じ経路（現在値、ADR-0020 規約 5）で行い、新しい表は作らない

### 5. バウンス・苦情

- v0 は **送信時の恒久的な拒否** だけを扱う: `ErrMailRejected` でジョブを `Fail` にし、失敗したジョブとしてダッシュボードに残す
- 非同期のバウンス（DSN）・苦情（フィードバックループ）は受けない。運用文書で、抑止リストを持つ送信事業者（SES のアカウントの抑止リストなど）を使うよう勧める
- 届かないアドレスを自前で記録するとき（後続）の形は、ADR-0020 に従ってイベント `email_delivery_failures`（`email_address_id`・種類 `bounce` / `complaint`・`occurred_at`・出どころ）と、
  identity が所有する投影 `email_suppressions`（現在止めているアドレス）にする。アドレスを確認し直すと解除のイベントで投影から外す

### 6. `mail/ses`

- **M6** で SES v2 の API（`sesv2.SendEmail`、Raw content）で作る。認証は SDK の既定の資格情報の連鎖（IAM ロール）で、SMTP のパスワードを持たない。設定はリージョンと任意の構成セット（configuration set）
- **M5** の間は、SES を使う運営者は SES の SMTP インタフェース（STARTTLS、587）を `mail = smtp` で使う。運用文書に例を載せる
- `mail/ses` は `testkit.MailerContract` を通す。恒久的な拒否を `ErrMailRejected` に写す

### 7. 運用文書

`docs/operations/email.md` を足す: 事業者ごとの設定例（SES の SMTP、一般的な SMTP の提出）、`mail_from` のドメインの SPF・DKIM・DMARC（`p=none` から始めて整合を確かめる）、送信の失敗の見方（`/admin/jobs` のメールのジョブの型で絞る、ADR-0064）、開発環境の Mailpit（#1026）。

### 覆る条件

- 運営者や利用者から HTML のメールの要望が強い、または主要な事業者でテキストだけのメールの到達率が明らかに悪いと分かったら、2B を別の ADR で決める
- 送信量が増えて、事業者の抑止リストだけでは送信の評判を保てない（自前の SMTP サーバーから直接送る運営者が多い）と分かったら、3B を作る
- 秘密をハンドラで発行すると、ジョブの実行が遅れる環境（Cloud Tasks の遅延など）でリンクの期限の扱いが不自然になると分かったら、1B（Sealer で封じたペイロード）を再検討する

## Consequences（影響）

- 良い影響
  - SMTP の障害が登録・リセットのリクエストを遅らせず、失敗は再試行され、ジョブのダッシュボードで見える
  - 秘密がメールの本文にしか現れない。SQS・Cloud Tasks のアダプタでもクラウドに秘密を置かない
  - ヘッダと配信停止で、通知のメールが主要な事業者の送信者要件に沿う（要検証、Open Questions）
  - すべてのメールが同じ外枠・ヘッダを持ち、ユースケースは本文だけを書く
- 悪い影響・トレードオフ
  - 登録の直後に「送れなかった」と利用者に返せなくなる。届かなければ利用者が再送を求める
  - ジョブの重複・再試行で、確認・リセットのメールが 2 通届くことがある（どちらのリンクも有効）
  - 配信停止のトークンの行がメールの数だけ増える（期限で消す。通知のメールの量は小さい）
  - プレーンテキストだけなので、ブランドの見た目は出せない
  - 非同期のバウンスを受けないので、事業者が抑止しない環境では届かないアドレスに送り続けうる
- 後続で必要になる作業（ADR の決定のあと、次の issue に分けて作る）
  1. ジョブ化: 確認・リセット・パスワードの通知をジョブにし、秘密の発行をハンドラに移す。`ErrMailRejected` と再試行の方針、`mail/smtp` の応答コードの分類、`testkit.MailerContract` の拡張
  2. 組み立てとヘッダ: `MailMessage` の拡張、共通の外枠、`From`・`Reply-To`・`Message-ID`・`Auto-Submitted`、`locales/en`・`locales/ja` のメッセージ
  3. 配信停止: `user_tokens` の用途 `email_unsubscribe`（スキーマ）、`/mail/unsubscribe` の `GET` / `POST`、`List-Unsubscribe` 系のヘッダ
  4. `mail/ses`（M6）: SES v2 の API、設定、コントラクトテスト
  5. 運用文書 `docs/operations/email.md`
  - 開発環境と結合テストの Mailpit は #1026 で別に進める

## Pros and Cons of the Options（詳細比較・任意）

### 1. 送り方

- **1A**: 良い — 秘密がペイロードに載らない。宛先・ロケールが実行時の値になる（ADR-0009 §2 と一致）。今のモデレーター・サポーターのジョブと同じ形。
  悪い — 用途ごとにハンドラを書く。秘密の発行がハンドラの中の DB 書き込みになり、ジョブの実行がトランザクションを 1 つ持つ
- **1B**: 良い — 送信の処理が 1 か所で、再試行・エラーの分類・計測をまとめやすい（Mastodon の ActionMailer + Sidekiq の `deliver_later` に近い。要検証）。トークンの発行は今の流れのまま。
  悪い — 組み立て済みの本文とアドレスがペイロードに載り、失敗したジョブの画面と SQS・Cloud Tasks に個人情報が残る。秘密を Sealer で封じても、KEK を持つ者には読め、`dead_jobs` の保持期間（30 日）残る。ロケールが投入時に固定される
- **1C**: 良い — 多くの場合すぐ届き、送れなかったことを応答で伝えられる（Misskey はリクエストの中で送ると見られる。要検証）。
  悪い — リクエストが SMTP の遅延に引きずられ、送信と再送の 2 つの経路を持つ。再送のジョブには結局秘密を渡す必要がある

### 2. 本文の形式

- **2A**: 良い — 作る・試す量が最小。HTML のサニタイズ・メールクライアントごとの表示差・ダークモードの問題がない。読み上げに強い。
  悪い — 見た目を整えられない。長い URL がそのまま出る。RTL の言語の表示はメールクライアントの双方向の処理に任せる（要検証）
- **2B**: 良い — 見た目・ボタン・ブランドを出せる。Mastodon・Misskey は HTML のメールを送る（要検証）。
  悪い — テンプレートを 2 系統持つ。明暗・RTL・クライアントごとの表示の試験が要る

### 3. バウンス・苦情

- **3A**: 良い — 受信の口（SNS の HTTPS エンドポイント、DSN を受けるメールボックス）を持たない。v0 の送信量では十分。
  悪い — 事業者が抑止しない環境では、届かないアドレスへの送信が続く
- **3B**: 良い — 送信の評判を自分で守れる。モデレーターに「届かないアドレス」を見せられる。
  悪い — SNS の署名検証・DSN の解析など、事業者ごとの受信の実装が要る。v0 の範囲を超える

### 4. `mail/ses`

- **4A**: 良い — IAM ロールで認証でき、長期の SMTP の資格情報を持たない（Lambda・ECS で自然）。aws-sdk-go-v2 は `queue/sqs` で既に依存している。
  悪い — アダプタとコントラクトテストを 1 つ増やす
- **4B**: 良い — 作るものがない。悪い — SMTP の資格情報（IAM ユーザーから派生）を秘密として管理する。Lambda から SMTP の接続を毎回張る

## Open Questions / 要検証

- 要検証: Gmail・Yahoo の送信者要件（SPF・DKIM・DMARC、`List-Unsubscribe` のワンクリックを求めるメールの種類と送信量の閾値、取引のメールが対象外か）。公式の文書で確かめて、§3 と運用文書に日付と出典を書く
- 要検証: SES v2 の `SendEmail` が `Message-ID` を付け替えるか、アカウントの抑止リストの既定の挙動と、抑止されたアドレスへの送信が同期のエラーになるか
- 要検証: Mastodon（ActionMailer の `deliver_later`、`List-Unsubscribe` の扱い）と Misskey（送信の方式・HTML のテンプレート）の実装
- 要検証: プレーンテキストのメールで、主要なメールクライアントが RTL の段落を正しく表示するか
- 取引のメールの期限（リセット 15 分・確認 1 時間）と再試行の回数が妥当か。実装の issue で値を確かめる
