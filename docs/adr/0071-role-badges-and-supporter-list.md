# ADR-0071: ロールのバッジと参加者の一覧

- Status: Proposed
- Date: 2026-10-22
- Deciders: @rosylilly
- Issue: #911

## Context（背景・課題）

M4.2（Supporters、epic #925）で、課金のプランに結び付いたロールのバッジをプロフィールに出し（FR-913）、管理者が有効にすればプランごとの参加者を一覧にする（FR-914）。

決定者の指示と回答（#925、原文の抜粋）:

> small プランは small-support ロールが紐付けられ、ロールに紐づいたバッジがプロフィールに掲出できる(ロールに紐づくバッジの掲出は個人ごとに有効化・無効化できる。デフォルト OFF)
>
> 管理者が有効にするなら各プランに誰が参加しているかをリストできるし、これを参加している各個人は掲載拒否できる
>
> 回答 7（バッジ）: → 検証不要で AP に載せない
>
> 回答 8（参加者の一覧）: 既定非掲載で OK。一覧を見られる範囲（誰でも / サインインした人だけ） → サーバー管理者が設定する

いまのロール（[data-model §4.1](../architecture/data-model.md)、`internal/domain/identity/role.go`）は、`roles`（`key`・`position`）・`role_permissions`・`user_role_grants` / `user_role_revocations`・投影 `user_roles` で、表示名も色も持たない。
ロールは権限の束で、利用者には見えない（`CredentialAccount.permissions` が本人の権限を返すだけ）。

プランとロールの連動（加入・解約・猶予でロールを付け外しする仕組みと、プランの資源）は ADR-A（#912）が決める。この ADR はバッジと一覧を決め、プランについては一覧が必要とする契約だけを決める。

決めること:

- バッジの属性（名前・色・アイコン・i18n）と、バッジを持てるロール
- 本人の掲出の ON/OFF（ロールごと、既定 OFF）、バッジを出す場所、API の形、ActivityPub との関係
- 参加者の一覧: 管理者の有効化、見られる範囲、本人の掲載、出す項目、ページと API、クローラーの拒否（[ADR-0057](0057-crawler-opt-out.md)）
- データモデル（[ADR-0020](0020-data-modeling-principles.md)）

関連: FR-720（ロール）、FR-910〜FR-917、[ADR-0058](0058-moderation-admin-separation.md)、[ADR-0009](0009-internationalization.md)、[ADR-0059](0059-design-tokens-and-instance-theme.md)、[ADR-0067](0067-finance-cost-records.md)。

### ほかの実装（要検証。この ADR では一次資料を確かめていない）

- Mastodon: ロールに名前・色（自由な 16 進）・`highlighted`（プロフィールにバッジを出す）を持たせる。出すかどうかはロールで決まり、本人は選べない。投稿の作者の表示には出ない。ActivityPub には載せない。
- Misskey: ロールに名前・色・アイコンの画像・「バッジとして出す」・「公開する」を持たせ、ノートの作者名の横にアイコンを出す。連合先には送らない。

決定者は AP に載せないことを検証不要と回答しているので、この ADR は上の挙動に依存しない。

## Decision Drivers（判断基準）

1. **支払いの事実を本人の同意なしに出さない**: バッジも一覧も、本人が選ぶまで何も出さない（決定者の回答 8。既定 OFF・既定非掲載）。権限の元（ロール・加入）がなくなれば表示も消える
2. **読みやすさと i18n（ADR-0009）を保つ**: どのテーマ（ライト・ダーク・サーバーのテーマ）でも文字の対比 4.5:1 を満たし、色だけで意味を伝えない。翻訳の無い文字列が UI の文言に混ざらない
3. **ロールの仕組みを 1 つに保つ**: 課金のロールも運用者のロールも同じ `roles` で、バッジだけのための第二のロールの仕組みを作らない（ADR-0058・FR-720）
4. **ADR-0020 のデータモデルに従い、読み出しを重くしない**: タイムラインの 1 件ごとに追加の読み出し（N+1）を足さない
5. **連合に漏らさない**: バッジも一覧も ActivityPub・NodeInfo に載せない（回答 7）
6. **小さく始める**: 最初の実装（#917・#922）が小さく、あとから広げられる

## Considered Options（選択肢）

### バッジの色

- **C1: 決まった色の名前（デザイントークン）から選ぶ**。`neutral`・`red`・`orange`・`yellow`・`green`・`teal`・`blue`・`purple`・`pink` の 9 色で、各色の背景と文字の組を `@my/ui` のトークンに置く
- **C2: 自由な色（16 進）を管理者が入れ、サーバーが対比を検査する**
- **C3: 自由な色を受け、文字の色（黒か白）をクライアントが選ぶ**

### アイコン

- **I1: アイコンを持たない**（名前と色だけ）
- **I2: ローカルのカスタム絵文字を 1 つ選べる**（ADR-0051）
- **I3: 画像を上げる**

### バッジを持てるロール

- **R1: どのロールにも付けられる**（`admin`・`moderator` を含む）。出すかどうかはいつも本人が選ぶ
- **R2: 課金のプランに結び付いたロールだけ**
- **R3: どのロールにも付けられ、運用者のロールはロールの設定で常に出す**（Mastodon の `highlighted` の形）

### 出す場所

- **P1: プロフィール（アカウント自身の取得）だけ**
- **P2: プロフィールと、投稿の作者の表示・アカウントの一覧**

### 本人の選択の持ち方

- **D1: 現在値の表**（行がある = 出す）。権限の元がなくなれば同じトランザクションで行を消す
- **D2: イベント（ON / OFF の記録）と投影**

### 一覧のページのクローラーへの表明

- **N1: いつも `noindex, noarchive`**
- **N2: サーバーの設定（`search_indexing`）と、載っている人の `indexable` に従う**

## Decision（決定）

> 推奨案。Accepted にするのは Decider のみ。

**C1・I1・R1・P1・D1・N1** を推奨する。

### 1. バッジの属性

- バッジはロールの属性で、1 つのロールに 0 か 1 つ。持つのは**名前**（`label`、1〜32 文字の 1 行）と**色**（C1 の 9 色の名前）だけである。
- 名前は管理者が書く文字列で、どのロケールでも同じ値を出す（インスタンスのルールと同じ扱い、data-model §4.9）。翻訳の機構は持たず、UI の文言ではなく利用者の内容として `dir="auto"` で描く。
  ロールの `key`（`small-support` など）は管理のための識別子で、利用者には出さない。
- 色は `@my/ui` のトークン `badge-<色>`（背景）と `badge-<色>-fg`（文字）の組で、ライトとダークの両方で 4.5:1 を `make web-tokens` が検査する。
  サーバーのテーマ（ADR-0059）はバッジのトークンを上書きしない。色は飾りで、意味は名前が運ぶ（WCAG 1.4.1）。
- アイコンは持たない（I1）。
- 組み込みのロールを含め、どのロールにもバッジを付けられ（R1）、既定ではどのロールもバッジを持たない。バッジの設定・変更・削除は `manage_roles` を持つ人が行い、FR-720 の位置の規則（自分のいちばん高いロール以下だけ）に従い、監査ログの `role_updated` に残す。
- 本人が出すかどうかは、運用者のロールでも課金のロールでも同じく本人が選ぶ（R3 の「常に出す」は持たない）。

### 2. 本人の掲出

- 利用者は、自分が持っていてバッジのあるロールごとに、プロフィールに出すかを選ぶ。既定は出さない。
- 出るのは「いま持っているロール（`user_roles`）で、バッジがあり、本人が出すと選んだもの」で、ロールの `position` の高い順に並べる。数の上限は置かない。
- ロールが剥奪されたとき（解約後の期間の終わり・支払いの失敗の猶予の後・返金を含む）と、ロールのバッジが削除されたときは、その選択を同じトランザクションで消す。もう一度付与されれば、また既定の「出さない」から始まる（判断基準 1）。
- プランの変更でロールが入れ替わるとき（small → medium）、プランの変更を 1 つのトランザクションで行う ADR-A（#912）は、古いロールの選択を新しいロールに引き継いでよい。`identity` はそのための操作（剥奪と付与を 1 つにし、選択を移す）を出す。引き継ぐかどうかは #912 が決める。

### 3. 出す場所と API

- バッジはプロフィールにだけ出す（P1）。Web では、プロフィールの見出し（表示名とハンドルの近く）に、見出しの付いたリスト（アクセシブルな名前は `client` の文言「バッジ」）で出す。投稿の作者の表示・通知・アカウントの一覧には出さない。
- API:
  - アカウント自身の取得（`Server.newProfile` が作る応答。`GET /accounts/{id}`・`GET /accounts/lookup`・`verify_credentials`）の `Account` に `badges`（`[{role_id, label, color}]`）を足す。一覧の `Account`（`newAccounts`・`presentStatuses`）では空の配列を返し、読みに行かない。リモートのアカウントはいつも空。
  - 本人の選択: `GET /preferences/badges`（`read:accounts`）が、持っていてバッジのあるロールごとに `{role_id, label, color, displayed}` を返し、`PUT /preferences/badges/{role_id}`（`write:accounts`、本文 `{displayed: bool}`）が変える。持っていないかバッジの無いロールは `404`。Web は `/settings/profile` にこの区画を置く。
  - 管理: `PATCH /admin/roles/{role}` の本文に `badge`（`{label, color}` か `null` で削除）を足し、`AdminRole` に `badge` を返す。`/admin/roles` の画面にバッジの名前と色を選ぶ欄と、見本を置く。
- ActivityPub: Actor の JSON-LD（`attachment`・`tag`・拡張の項目を含む）、NodeInfo、WebFinger のどれにもバッジを載せない。リモートのバッジも取り込まない。

### 4. 参加者の一覧

- インスタンス設定のキー `supporter_list_visibility`（`enum(off, public, signed_in)`、未設定は `off`）を `instance` に足す。`manage_settings` で守り、サーバーの設定の画面から変える（ADR-0067 の `finance_visibility` と同じ扱い）。
  - `off`: API は `404`、Web は一覧への導線を出さない。
  - `public`: 誰でも見られる。
  - `signed_in`: このサーバーにサインインした人だけが見られる。サインインしていなければ API は `401`、Web はサインインへ案内する。
- 本人の掲載: 加入している利用者が、自分を一覧に載せるかを選ぶ。既定は載せない。選択は利用者ごとに 1 つで、プランごとには持たない（同時に加入できるプランは 1 つ、決定者の回答 10）。プランを変えても選択は残り、加入が終わったとき（ロールが外れる時と同じ）に同じトランザクションで消える。
- 出す項目: プランごとの見出し（プランの名前、プランの並び順）と、各人のアバター・表示名・ハンドル・プロフィールへのリンクだけを出す。
  金額・月払いか年払いか・加入した日・続けた期間・人数の合計は出さない。人数は収入の公開（ADR-E、#914）の範囲の設定に従う情報で、一覧の行の数を数えても載せた人の数しか分からない。
- 一覧に出す人は、閲覧者に見せられるアカウント（[visibility.md §6](../architecture/visibility.md#6-アカウントの表示)、`Server.visibleAccount` と同じ規則。凍結・制限されたアカウントと、閲覧者とブロックの関係にあるアカウントを除く）に限る。並びは載せた順（新しい順）で、カーソルでページを送る。
- ページは Web の `/about/supporters` で、`/about` から `supporter_list_visibility` が `off` でないときにリンクする。
- API（タグ `instance`）: `GET /instance/supporters?plan_id=&cursor=`。`public` のときは `security: []`、`signed_in` のときはトークンを要する（`read:accounts`）。`Cache-Control` は `public` のとき `public, max-age=60`、`signed_in` のとき `private, no-store`。
  `GET /instance` に `supporter_list_visibility` を足し、Web はそれで導線を出し分ける。本人の掲載の選択は `GET/PUT /preferences/supporter_listing`（`{listed: bool}`）で、加入していなければ `PUT` は `404`。
- クローラー: `/about/supporters` の外枠と API の応答は、サーバーの設定に関わらずいつも `noindex, noarchive`（meta と `X-Robots-Tag`）にする（N1）。AI の表明は ADR-0057 のとおりサーバーの設定に従う。一覧は ActivityPub・NodeInfo に出さない。

### 5. プランとの契約（ADR-A、#912 が満たす）

この ADR はプランの資源と加入の状態を決めない。一覧と掲載の選択のために、#912 のプランのモジュールに次を求める。

- プランの一覧（`id`・名前・並び順・結び付くロール）を読める。廃止したプランは一覧に出さない。
- 「いまプラン X に加入している利用者」を、ロールが付いている期間と同じ定義で列挙できる（解約後の期間の終わりまでは加入中、猶予の間も加入中）。
- 掲載の選択の表（6.）を持ち、加入が終わる処理と同じトランザクションでその行を消す。
- 上位のプランの人は、上位のプランの見出しにだけ出る（ロールは 1 つだけ付く、決定者の回答 10）。

### 6. データモデル（D1）

| テーブル | 分類 | 持つモジュール | カラム | 制約 |
| --- | --- | --- | --- | --- |
| `role_badges` | 現在値 | `identity` | `role_id`（PK）, `label`（`string(32)`）, `color`（`enum(neutral, red, orange, yellow, green, teal, blue, purple, pink)`）, `updated_at` | 行がある = バッジがある |
| `user_role_badge_displays` | 現在値 | `identity` | `user_id`, `role_id`, `created_at` | PK `(user_id, role_id)`。行がある = 出す |
| `supporter_listings` | 現在値 | #912 のプランのモジュール | `user_id`（PK）, `created_at` | 行がある = 載せる |

- インスタンス設定は `instance_setting_revisions` のキー `supporter_list_visibility` で、`instance_settings` の投影に入る。
- 「選んだか」を NULL 許容の列や真偽の列で持たず、行の有無で表す（ADR-0020 規約 4）。本人の選択は履歴を問わない設定で、`user_preferences` と同じく現在値にする（D1）。
- ロールの剥奪（`user_role_revocations` を足す処理）とバッジの削除が `user_role_badge_displays` を、加入が終わる処理が `supporter_listings` を、同じトランザクションで消す。ロールの削除は持っている人がいないときだけできる（data-model §4.1）ので、`role_badges` の行もそのとき消す。
- プロフィールのバッジは `user_roles`・`role_badges`・`user_role_badge_displays` の結合 1 回で読み、アカウント自身の取得でだけ行う（判断基準 4）。

この決定を見直すきっかけ: 投稿の作者の表示にもバッジを求める声が強いとき（P2。タイムラインの読み出しに 1 回の結合を足す設計が要る）。
名前を言語ごとに変えたい運用者が多いとき（ロケールごとの名前の表）。アイコンを求められたとき（I2。カスタム絵文字の ID を `role_badges` に足す）。

## Consequences（影響）

- 良い: 本人が選ぶまで、バッジも一覧も何も出さない。権限の元がなくなれば表示も消え、再加入しても既定に戻る。
- 良い: 色はトークンの組なので、どのテーマでも対比が保証され、管理画面で対比の誤りを説明する作業が要らない。
- 良い: ロールの仕組みは 1 つのままで、運用者のロール（`moderator` の「スタッフ」など）にも同じバッジが使える。
- 良い: タイムラインの読み出しは変わらない。ActivityPub の形式も変わらない。
- 悪い: 色は 9 色だけで、サーバーのブランドの色をバッジに使えない。
- 悪い: アイコンが無く、Misskey のような絵のバッジは作れない。
- 悪い: 名前は 1 つの値で、多言語のサーバーでは管理者がどの言語で書くかを選ぶ必要がある。
- 悪い: 運用者のロールのバッジも本人が出さなければ出ず、「この人はモデレーター」と示すことをサーバーが強制できない。
- 悪い: 投稿の作者の表示にバッジが無いので、サポーターであることはプロフィールを開かないと分からない。
- 悪い: プランを変えると、#912 が引き継がない限りバッジは「出さない」に戻る。
- 悪い: 一覧はいつも `noindex` で、サーバーが検索を許していても検索エンジンに載らない。
- 後続 #917（ロールのバッジ）:
  - schema の `role_badges`・`user_role_badge_displays`（全方言）、[data-model §4.1](../architecture/data-model.md) の表と規則（剥奪とバッジの削除で選択を消す）
  - `internal/domain/identity` のバッジの型と色の enum、`identity.Service` の設定・選択・読み出しと、剥奪と付与を 1 つにして選択を移す操作
  - OpenAPI: `Account.badges`、`AdminRole.badge`、`PATCH /admin/roles/{role}` の `badge`、`GET /preferences/badges`・`PUT /preferences/badges/{role_id}`
  - `@my/ui` のバッジの部品とトークン `badge-<色>` / `badge-<色>-fg`（`make web-tokens` の組）、プロフィールの見出し、`/settings/profile` の区画、`/admin/roles` の欄
  - `locales/en`・`locales/ja` の文言（バッジの見出し、設定の説明、色の名前）
  - テスト: 出すと選んだ本人のプロフィールにだけ出る、一覧の `Account` は空、Actor の JSON-LD に入らない
- 後続 #922（参加者の一覧の部分）:
  - インスタンス設定 `supporter_list_visibility`（`instance_setting_revisions` の enum、[data-model](../architecture/data-model.md)、サーバーの設定の画面）と `GET /instance` の項目
  - `supporter_listings`（#912 のモジュール、全方言）と、加入が終わる処理で消すこと
  - `GET /instance/supporters`・`GET/PUT /preferences/supporter_listing`、[client-api.md](../architecture/client-api.md) の公開の API の表
  - Web の `/about/supporters`・`/about` の導線・設定の画面の掲載の区画、外枠の `noindex, noarchive`（ADR-0057 の表に行を足す）
  - テスト: 載せた人だけが出る、`off` は `404`、`signed_in` はサインインしていなければ `401`、金額や加入日を返さない
- 後続 #912: §5 の契約を ADR-A に書く（プランの一覧、加入中の定義、`supporter_listings` の持ち主、プランの変更でバッジの選択を引き継ぐか）。

## Pros and Cons of the Options（詳細比較・任意）

### C1: トークンの色の名前

- 良い: ライト・ダーク・サーバーのテーマのどれでも対比を `make web-tokens` で保証できる。API とデータが enum で小さい。
- 悪い: 色の選択が狭い。トークンを増やすたびに 2 つのテーマの組を足す。

### C2: 自由な色と対比の検査

- 良い: ブランドの色を使える。Mastodon・Misskey と同じ自由度。
- 悪い: ライトとダークで同じ色が両方の背景に対して読めるとは限らず、テーマごとの色を入れさせるか、片方で落ちる。サーバーのテーマ（ADR-0059）で背景が変わると検査をやり直す必要がある。

### C3: 自由な色と文字の色の自動選択

- 良い: 入力が 1 つで済み、バッジの中の文字は読める。
- 悪い: バッジの背景と周りの背景の対比（非文字の 3:1）は保証できない。黒か白の文字は、中間の明るさの色で 4.5:1 に届かないことがある。

### I1: アイコンなし

- 良い: 画像の保存・代替テキスト・モデレーションが要らない。小さく始められる。
- 悪い: 見た目の表現が名前と色に限られる。

### I2: ローカルのカスタム絵文字

- 良い: 既存の資源（ADR-0051）を使い、画像の保存を足さない。代替テキストはショートコードから作れる。
- 悪い: 絵文字の削除・無効化とバッジの関係（消えたら外すか）を決める必要がある。名前の横に画像が付くと、小さな幅での配置と読み上げの順を設計し直す。

### R1: どのロールにも付ける

- 良い: 仕組みが 1 つで、運用者のロールにも使える。課金のロールかどうかを判定する必要がない。
- 悪い: 運用者が「スタッフ」を示したくても本人の選択に任せる。

### R2: 課金のロールだけ

- 良い: FR-913 の最小の範囲で、運用者のロールに関わる判断が要らない。
- 悪い: ロールに「課金のロールか」の区別を持ち込み、#912 の連動に依存する。運用者のバッジを後で足すときに作り直す。

### R3: 運用者のロールは常に出す

- 良い: 誰がモデレーターかを利用者が知れる（Mastodon の形）。
- 悪い: 決定者の「個人ごとに有効化・無効化できる。デフォルト OFF」と、ロールによって違う規則になる。モデレーターであることを出したくない人の選択が無くなる。

### P1: プロフィールだけ

- 良い: 決定者の指示の範囲で、読み出しはアカウント自身の取得にだけ足す。タイムラインの見た目が変わらない。
- 悪い: 投稿を読むだけではバッジが見えない。

### P2: 投稿の作者の表示にも出す

- 良い: Misskey や X Premium のように、どこでもサポーターと分かる。
- 悪い: タイムラインの全件の作者についてロールとバッジを読む。作者の表示が混み、狭い幅で表示名を圧迫する。

### D1: 現在値の表

- 良い: 読み出しが単純で、`user_preferences` と同じ扱い。消すことが「既定に戻す」に一致する。
- 悪い: いつ出し始めたかの履歴が残らない（必要とする要件はない）。

### D2: イベントと投影

- 良い: 出した・止めた履歴を残せる。
- 悪い: 履歴を読む機能が無く、表と投影の維持が増える。本人の個人的な選択の履歴を長く持つこと自体が、判断基準 1 に反する。

### N1: いつも `noindex`

- 良い: 支払いの事実を集めたページが検索に載らない。載っている人の `indexable` がまちまちでも、ページ単位で判断せずに済む。
- 悪い: サポーターを宣伝したい運用者の意図に反することがある。

### N2: 設定に従う

- 良い: ADR-0057 のほかのページと同じ規則。
- 悪い: 載っている人の 1 人でも `indexable = false` なら拒否するのか、ページ単位の規則を新しく決める必要がある。本人が一覧への掲載を選んでも、検索への掲載まで選んだとは限らない。

## Open Questions / 要検証

- プランの変更でバッジの選択を引き継ぐか（§2）。この ADR は引き継げる操作だけを用意し、#912 で決める。
- 「ほかの実装」の節の Mastodon と Misskey のロールの属性は一次資料で確かめていない（決定には効かない）。
