# ADR-0039: モバイルのナビゲーションの項目と投稿の入口

- Status: Accepted
- Date: 2026-10-17
- Deciders: @rosylilly
- Issue: #328, #660

## Context（背景・課題）

Web クライアントの外枠（[web-client.md §9](../architecture/web-client/09-app-shell.md#9-アプリの外枠)）は、`md` 未満の画面で下端のタブバーにナビゲーションの項目を並べ、投稿のフォームを浮かぶボタンから開く。
M3.5 の UI 監査（#328）で、実際のサーバーとクライアントを 320 / 390 px × `en` / `ja` / `ar-XB` で表示すると、次のことが分かった。

- ホーム・ローカル・連合・検索・通知・プロフィール・設定の 7 項目を等分に並べると、1 項目の幅が 45〜55 px になり、`en` と `ar-XB` で項目名が「Fed…」「Noti…」「Setti…」のように切れる。
  名前が切れたナビゲーションは、見える名前で探す利用者（音声入力・認知の負担）に向かない（WCAG 2.5.3 の考え方）。
- 「投稿を書く」の文言付きの浮かぶボタンは、320 px で画面幅の約半分を占め、タイムラインの本文と操作を隠す。検索・設定・フォローの一覧のような投稿と関係のない画面にも出る。
- 主要な類似クライアントは下端の項目を 5 つ以下にしている（Mastodon Web: ホーム・検索・投稿・通知・メニュー、[navigation_bar.tsx](https://github.com/mastodon/mastodon/blob/main/app/javascript/mastodon/features/ui/components/navigation_bar.tsx)。Misskey: 投稿ボタンを含む 5 つ前後、[mobile-footer-menu.vue](https://github.com/misskey-dev/misskey/blob/develop/packages/frontend/src/ui/_common_/mobile-footer-menu.vue)。Elk: [NavBottom.vue](https://github.com/elk-zone/elk/blob/main/app/components/nav/NavBottom.vue)）。

決定者は、ローカルと連合のタイムラインを 1 つの画面のタブにせず、別の場所に置くと指示している（[#660](https://github.com/mycroblog/my/issues/660)「タイムラインをローカル・連合でタブ化しない。分離して配置。」）。
ナビゲーションの項目は情報設計の決定で、画面ごとの修正では決まらないので、ここで決める。関連する要件は FR-201〜207（タイムライン）、NFR-A11Y-1。

## Decision Drivers（判断基準）

1. 決定者の指示: ローカルと連合のタイムラインは、それぞれ独立した場所にする（#660）
2. 320 px のどのロケールでも、すべての項目名が省略されずに読める（D3、NFR-A11Y-1）
3. よく使う場所（ホーム・ローカル・連合・通知）と投稿に 1 回で届く
4. ローカルと連合のタイムラインを無効にしたサーバー（FR-202）でも、同じ形で破綻しない
5. 他のクライアントから来た利用者が迷わない

## Considered Options（選択肢）

1. 7 項目（ホーム・ローカル・連合・検索・通知・プロフィール・設定）を並べ、項目名を `text-xs` で 2 行まで折り返す
2. 下端は 6 項目（ホーム・ローカル・連合・通知・検索・メニュー）。プロフィール・ブックマーク・設定は「メニュー」のシートにまとめる。投稿のボタンはアイコンだけの浮かぶボタンにする
3. 下端は 5 項目（ホーム・タイムライン・通知・検索・メニュー）。ローカルと連合は「タイムライン」の画面のタブにし、ほかは選択肢 2 と同じにする
4. 下端は 5 項目（ホーム・検索・投稿・通知・メニュー）。投稿はタブバーの中央のボタンにし、浮かぶボタンはなくす（Mastodon Web と同じ）

## Decision（決定）

**選択肢 2 を採用する。**

- 7 項目（選択肢 1）は、`ar-XB` と `en` で 2 行にしても 320 px で切れる項目が残り、プロフィールと設定という頻度の低い場所がタブバーの幅を使う。
- 選択肢 3 は項目が 5 つで済むが、ローカルと連合が 1 つの画面のタブになり、決定者の指示（判断基準 1）に反する。どちらかのタイムラインに移るのに 1 タップ多くかかる。
- 選択肢 4 はタブバーに「場所でない項目」（投稿）が混ざり、`aria-current` の付く項目と付かない項目が並ぶ。投稿の入口が `md` 以上（浮かぶボタン）と違う形になり、ローカルと連合のどちらかもタブバーに入らない。
- 選択肢 2 は、場所（ナビゲーション）と操作（投稿）を分けたまま、ローカルと連合をそれぞれの項目にできる。
  - ローカル（`/local`）と連合（`/public`）は、どの幅でもナビゲーションの別の項目・別の画面にする。どちらの画面もそのタイムラインだけを置き、もう一方へのタブを持たない。
  - タブバーのタイムラインの項目は、インスタンスが提供するタイムライン（`GET /instance` の `timelines`）だけを出すので、項目の数は 4〜6 つになる。無効にしたサーバーでは項目が減るだけで、形は変わらない。
  - 項目名は省略しない。各項目は文言の幅を基本にして残りの幅を分け合い、6 つが 320 px に収まらない翻訳では単語の途中でも折り返して、全体を読めるようにする。
  - 浮かぶボタンは `md` 未満でアイコンだけ（アクセシブルネームとツールチップは「投稿を書く」）にし、タイムラインとプロフィールの画面にだけ出す。
  - `md` 以上のレールとサイドバーは、ホーム・ローカル・連合・通知・検索・プロフィール・ブックマーク・設定を並べる。タブバーと同じ 1 つのリストの同じ順番で、その幅で出ない項目を隠す。
  - ブックマークの一覧の入口は、`md` 以上のレールとサイドバー（プロフィールと設定の間）と「メニュー」のシートに置き、タブバーには置かない。
    「メニュー」のシートには、タブバーにないレールの項目をレールと同じ順（プロフィール・ブックマーク・設定、権限のある閲覧者にはモデレーションと管理、[ADR-0058](0058-moderation-admin-separation.md)）で並べる。

覆る条件: 6 つの項目では折り返しても読みにくい（3 行以上になる）ロケールを加える場合や、利用の計測でタブバーの項目の使われ方が大きく偏ると分かった場合は、タブバーの項目の選び方を見直す。

## Consequences（影響）

- 320 px でもすべての項目名が省略されずに読め、浮かぶボタンが本文を隠さない。
- ローカルと連合のタイムラインに、どの幅でも 1 タップで届く。
- 6 つの項目では 1 項目の幅が狭く、長い翻訳では項目名が単語の途中で折り返し、タブバーの高さが増える。
- プロフィールと設定は 1 タップ遠くなる。「メニュー」のシートという、新しい画面の型が 1 つ増える。
- レイアウトの詳細は [web-client.md §9](../architecture/web-client/09-app-shell.md#9-アプリの外枠) が受け持つ。
