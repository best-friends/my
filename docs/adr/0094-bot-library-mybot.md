# ADR-0094: ボット制作ライブラリ pkg/mybot

- Status: Accepted
- Date: 2026-10-23
- Deciders: @rosylilly
- Issue: #1066

## Context（背景・課題）

決定者は M5 の作業として、API クライアントライブラリ `pkg/mykit`（[ADR-0093](0093-api-client-library-mykit.md)、#1065）と、その上でボットを少ないコードで書ける
ライブラリ `pkg/mybot` を Go と TypeScript（npm）で出すと決めた。プロフィールには bot フラグがあり（FR-006、`Account.bot`）、
サードパーティのアプリの登録は [ADR-0090](0090-third-party-oauth-apps.md)（#1038）で決める。

`mykit` だけでもボットは書けるが、どのボットの作者も同じ問題を自分で解くことになる:

- イベントの受け取り: `/api/v1/streaming`（SSE、FR-207）はイベントに `id` を付けず、`Last-Event-ID` で再開できない（[client-api §5](../architecture/client-api.md#5-ストリーミング)）。
  切れていたあいだのメンションを取りこぼさないには、通知の一覧（`listNotifications`、新しい順のキーセットページング）を読み直して突き合わせる必要がある。
- 重複: SSE と一覧の読み直しの両方で同じ通知が届く。同じメンションに 2 回返信すると、利用者にも連合先にも迷惑になる。
- 振る舞い: ボット同士の無限の応答の連鎖、`direct`・`local`（ADR-0017）の投稿への返信の公開範囲の広げすぎ、レート制限（ADR-0019 §5、投稿 300 / 3 時間・アカウント 1,500 / 5 分）の超過は、
  作者が気を付けなければ起こる。既定で安全な側に倒す層が要る。

サーバー単位の webhook（ADR-0060）は管理者が `manage_webhooks` で設定するもので、イベントも管理向け（通報・登録など）に限られ、利用者の通知は送らない。ボットには使えない。

`mykit` の公開の仕組みと同時に決めないと、`mybot` の名前・版・依存の向きが後で `mykit` とずれるので、いま決める。

## Decision Drivers（判断基準）

1. **取りこぼさず、2 回応答しない**: 切断・再起動・再試行のあとでも、各メンションに高々 1 回だけ返す。ADR-0003 の冪等キーの方針を利用者側でも守る。
2. **既定で行儀がよい**: ボット同士の連鎖・公開範囲の広げすぎ・レート制限の超過を、作者が何も書かなくても起こさない。
3. **サーバーに新しい機能を要求しない**: いまの client API（SSE・通知の一覧・`Idempotency-Key`）だけで動く。サーバーの費用（ゼロに近い運用、vision）を増やさない。
4. **少ないコード**: エコーのボットが 20 行ほどで書ける。Go と TS で同じ概念を、それぞれの言語の慣用の形で出す。
5. **`mykit` との境界が明確**: HTTP・認証・API の型は `mykit` に置き、`mybot` はその上の振る舞いだけを持つ。
6. **動かす場所を選ばない**: 常駐の VM・コンテナ・ノート PC のどれでも動き、追加の DB やキューを必須にしない。

## Considered Options（選択肢）

1. **SSE + 通知の一覧での追いつき + 処理済みの記録のポート（ライブラリだけ）**: 常時 SSE を読み、接続のたび（起動・再接続）に通知の一覧を前回の位置まで読み直す。
   処理済みの位置と ID をライブラリの `Store` ポートに記録し、既定の実装（メモリ・ファイル）を同梱する。ボットはライブラリとして組み込み、ランナーは出さない。
2. **通知のポーリングだけ + サーバーの既読のマーカーを位置にする**: 一定間隔で通知の一覧を読み、`notifications/marker` の `last_read_id` を処理済みの位置にする。ボット側に状態を持たない。
3. **ボット向けの webhook（サーバーに新設）+ `mybot` は HTTP の受け口のフレームワーク**: ADR-0060 を利用者単位に広げ、通知を Standard Webhooks の形でボットの URL に送る。
4. **ランナー中心**: `mybot` の CLI とコンテナのイメージを出し、設定ファイルとスクリプト（TS）を読み込んで動かす。イベントの受け取りは 1 と同じ。

## Decision（決定）

**選択肢 1 を採用する。** ボットの作者が書くのはハンドラだけで、取りこぼしと重複の扱い・行儀の既定・レート制限はライブラリが持つ。
選択肢 2 の「状態を持たない」利点は、refresh token のローテーションを保存する必要がある以上（§7）どの形でも得られず、`Store` は 1 ファイルの `FileStore` を既定にして手間を抑える。

### 1. 配置・ライセンス・公開

[ADR-0093](0093-api-client-library-mykit.md) の §1・§2・§7・§8 にすべて揃え、違えるところはない。

- Go: `pkg/mybot/` を別のモジュール `github.com/mycroblog/my/pkg/mybot`（パッケージ名 `mybot`、タグ `pkg/mybot/vX.Y.Z`）にし、`mykit` だけに依存する。
  `go.mod` はサーバーのモジュールを require しない（ADR-0093 と同じ検査）。最小の Go の版と `CGO_ENABLED=0` も `mykit` と同じ。
- TS: `pkg/mybot/ts/` に `@mycroblog/mybot` を置き、`@mycroblog/mykit` を `dependencies` に置く（同じ版の組で動作を確かめるため）。ESM のみで、対象のランタイムは `mykit` と同じ（Node.js 22 以降・Bun・Deno。ブラウザでの動作は約束しない）。
- ライセンス: ADR-0093 のとおり MIT（`pkg/mybot/LICENSE`、SPDX ヘッダ `MIT`）。依存は寛容なライセンスのものだけ。
- 版と公開: サーバー・`mykit` と同じ版の番号で同じリリースに出す（#1029 の仕組み、npm は trusted publishing）。ライブラリの破壊的変更の扱いは ADR-0093 §8 と同じで、`mybot` が呼ぶ `/api/v1` の変更は [ADR-0090](0090-third-party-oauth-apps.md) §8 の約束に従う。
- 外部の依存は最小にする。Go・TS とも `mykit` と言語・実行環境の標準（`fetch`・`AbortSignal`）だけで書き、TS の cron の式の解釈だけを依存にする（§5）。

### 2. 境界（`mykit` と `mybot`）

| 持つもの | `mykit` | `mybot` |
| --- | --- | --- |
| HTTP・型付きの API・問題の詳細のエラー | ○ | 使うだけ |
| アクセストークンの付与と refresh token のローテーション（`TokenSource`） | ○ | 新しいトークンを受けるコールバック（`onTokens`）で `Store` に保存する |
| SSE の読み取り・ハートビート・再接続（バックオフ、`Retry-After`） | ○ | 接続のたびの追いつき（§3） |
| `429`・`503` の `Retry-After` に従う再試行、`Idempotency-Key` の付与 | ○ | 決まった冪等キー（§6）と送信の予算を上乗せ |
| イベントの振り分け・コマンド・ミドルウェア・定期実行・処理済みの記録・テストの道具 | | ○ |

`mykit` に足りないもの（例: SSE のクライアントを持たない）があれば、`mybot` で補わず `mykit` に足す。

### 3. イベントの受け取り

- 起動すると `verifyCredentials` で自分のアカウントを確かめ（§7）、SSE（`/api/v1/streaming`）を開く。
- **追いつき**: SSE を開くたび（起動と再接続）、開いた後に `listNotifications` を新しい順に読み、`Store` の処理済みの位置（最後に処理した通知の ID）より古いものに届くか、
  追いつきの上限（既定 24 時間より古い通知。設定で変える、0 で追いつかない）に届いたところで止め、古い順に処理する。
  SSE を先に開くので、読み直しの最中に来た通知も落ちない（重複は次の項で除く）。
- **重複の除去**: 通知の ID（UUIDv7 で時系列に並ぶ）ごとに処理済みを `Store` に記録し、記録済みの ID は処理しない。記録は既定で 7 日（追いつきの上限より長い）で捨てる。
- **ハンドラの後に記録する**（at-least-once）。ハンドラの途中でプロセスが止まると同じ通知をもう一度処理することがあるので、返信などの書き込みは §6 の冪等キーで 2 度目を無害にする。
- 再接続（バックオフ・`Retry-After`・ハートビートの途絶の検出）は `mykit` の SSE のクライアントに任せ、`mybot` は `mykit` が知らせる「(再)接続した」を合図に追いつきを走らせる。
- SSE の `update`（ホームの新着）は、作者が `OnStatus` を登録したときだけ扱う。ホームの新着は追いつきをせず、切れていたあいだの分は届かない（文書に書く）。
- ポーリングだけの動き方（選択肢 2 の形）も `Mode: Polling`（間隔の既定 60 秒）として持つ。SSE が通らないプロキシの環境と、短命の実行（cron で起動して追いついたら終わる `RunOnce`）のため。

### 4. ハンドラの形

通知の種類（`NotificationType`）に対応するハンドラを出し、Go と TS で同じ名前の概念にする。

| ハンドラ | 起きるとき |
| --- | --- |
| `OnMention` | `mention`。返信・`direct` の投稿（DM）を含み、文脈に `IsReply`・`IsDirect` を持つ。サーバーは公開範囲によらず、投稿の版が新しくメンションしたアカウントに `mention` を作る（`internal/app/notification/projection.go` の `projector.mentions`） |
| `OnCommand(name, ...)` | `OnMention` のうち、本文の先頭の自分へのメンションを除いた最初の語が `name` のもの（例: `@bot help`） |
| `OnFollow` / `OnFollowRequest` | `follow` / `follow_request` |
| `OnReaction` / `OnFavourite` / `OnBoost` / `OnQuote` | 同名の通知 |
| `OnNotification` | どの種類でも（上のどれにも当たらないものを含む） |
| `OnStatus` | SSE の `update`（§3） |
| `Every(cronExpr, ...)` | 定期実行（§5） |

- 本文は HTML なので、ライブラリが平文に直したもの（メンション・リンクを文字列にする）を文脈に入れる。コマンドの解析は、先頭の自分へのメンションを除き、空白で区切った最初の語をコマンド名、残りを引数の文字列にする。
  名前は大文字と小文字を区別しない。どのコマンドにも当たらないメンションは `OnMention` に落ちる。`help` は登録したコマンドの説明から既定で答える（無効にできる）。
- 文脈（Go は `*mybot.Context`、TS は `ctx`）は、元の通知・投稿・送り手と、`Reply(text)`・`React(emoji)`・`Follow()` などの補助を持つ。補助は §6 と §8 の既定を守る。
- **ミドルウェア**: Go は `func(mybot.Handler) mybot.Handler`、TS は `(ctx, next) => Promise<void>`。既定で次を順に入れる: パニック・例外の回収とログ、§8 の行儀の検査、§6 の送信の予算。
  作者は権限（例: 管理者のアカウントだけが使えるコマンド）・ログの形などを足せる。ログは Go が `log/slog`、TS は `console` 互換の受け口にする。
- 並行: ハンドラは既定で最大 4 つ同時に動かし、同じ送り手の通知は順に処理する（`Status` は会話の ID を持たないので、送り手で分ける）。

### 5. 定期実行

- `Every("0 9 * * *", handler, opts)` で 5 フィールドの cron の式（分 時 日 月 曜日）とタイムゾーン（既定は UTC、IANA の名前で指定）を受ける。
- 式の解釈: Go は 5 フィールド（数・範囲 `a-b`・刻み `*/n`・列挙 `a,b`）だけを `mybot` の中で自作し、依存を持たない。秒のフィールドや `@daily` などの別名は受けない。
  TS は `croner`（MIT、依存なし、Node・Deno・Bun で動く。2026-10-23 に npm の `croner` の最新が 10.0.1（2026-02 公開）で、github.com/hexagon/croner が保守中であることを確認）で式を解釈し、次の時刻の計算だけに使う。
  Go と TS で受ける式の範囲を揃えるため、TS でも 6 フィールドと別名を `mybot` の側で拒否する。
- **止まっていたあいだの扱い**: 既定は飛ばす（起動の後の次の時刻から動く）。`CatchUp: Latest` を指定すると、`Store` の最後に実行した時刻より後の予定のうち、最も新しい 1 回だけを起動時に実行する。
  何回分も溜まった分をまとめて投稿することはしない。
- 定期実行のハンドラが投稿するとき、冪等キーは `mybot:every:<名前>:<予定の時刻 RFC 3339>` にする（§6）。同じボットを誤って 2 つ動かしても、同じ時刻の投稿は 1 つになる。

### 6. 冪等とレート制限

- **冪等キー**: `Reply` と定期実行の投稿は、`createStatus` に決まった `Idempotency-Key` を付ける。返信は `mybot:reply:<通知 ID>:<そのハンドラの中での番号>`。
  サーバーはアカウントごとにキーを覚えているので（`local_statuses` の一意制約）、§3 で同じ通知をもう一度処理しても投稿は 1 つになる。作者が `mykit` を直接使って投稿するときのために、同じ規則でキーを作る関数も出す。
  お気に入り・リアクション・フォローは、spec のとおり 2 度目の呼び出しが何も変えずに成功するので（`favouriteStatus`・`reactToStatus`・`followAccount` の説明）、キーを付けない。
- **処理済みの記録**: `Store` ポート（Go はインタフェース、TS は型）で、処理済みの通知の ID・追いつきの位置・定期実行の最後の時刻・refresh token を持つ。
  同梱する実装は `MemoryStore`（試験向け。再起動で消える。§7）と `FileStore`（JSON の 1 ファイル、書き込みは一時ファイルからの rename）。
  既定は `FileStore`（`./mybot-state.json`）。DB などを使いたい作者は `Store` を実装する。
  サーバーの既読のマーカー（`notifications/marker`）は位置に使わない。ボットのアカウントを人が Web で開くとマーカーが進み、ボットが未処理の通知を飛ばすため。
- **送信の予算**: `mykit` の `429` の再試行に加え、`mybot` は送信の前にクライアント側のトークンバケットで待つ。既定は投稿が 1 時間に 60（サーバーの 300 / 3 時間の 6 割）、
  そのほかの書き込みが 1 分に 60。応答の `RateLimit` ヘッダの残りが 1 割を切ったら次の窓まで待つ。予算を超えた返信は捨てずに待たせ、待ちが 10 分を超えたものはログに出して捨てる。

### 7. 認証と bot フラグ

- 認証は `mykit` の `TokenSource` をそのまま受ける。固定のアクセストークンか、refresh token で更新するもの（ADR-0093 §5）で、取得の手順は持たない。トークンの取り方は [ADR-0090](0090-third-party-oauth-apps.md) に従い、README に書く。
  主な手順は、ボットのアカウントでログインし、設定の画面でアプリ（confidential client）を登録して、登録者自身へのトークンを redirect なしに発行すること（ADR-0090 の「登録者自身へのトークン発行」）。
  このトークンは長命のトークンではなく、ふつうのアクセストークンと refresh token の組なので、`mybot` は `mykit` の refresh token で更新する `TokenSource` を使う。
  `client_credentials` はないので、ボットは必ずボット用のアカウントの利用者として動く。Authorization Code + PKCE で認可したい作者のために、ループバックのリダイレクトで受け取る小さな例（`examples/login`）を置く。
- refresh token がローテーションされたら（`mykit` の `onTokens`）、`mybot` が新しいものを `Store` に保存する。`mykit` はトークンを保存しないので、ここが `mybot` の足す分になる。古いものを使い回すと RFC 9700 の検出で系列ごと失効するため。
  起動時は `Store` に保存した refresh token を、設定で渡した最初の refresh token より優先する。`MemoryStore` では再起動のたびに最初の refresh token に戻り、それは使用済みなので失効する。`MemoryStore` は試験のためのもので、常駐のボットも `RunOnce` を繰り返し起動するボットも永続の `Store` を使う（README に書く）。
- 要るスコープ: 既定のハンドラの組で `read:notifications`・`read:statuses`（SSE に要る）・`write:statuses`。起動時に足りなければ、足りないスコープを挙げて止まる。
- **bot フラグ**: 起動時に `verifyCredentials` の `bot` を確かめ、偽なら既定ではエラーで止まる。`SetBotFlag: true` を指定すると `updateCredentials` で立てる（`write:accounts` が要る）。
  確かめずに動かすには `AllowNonBot: true` を明示する。どのアプリから投稿しても bot フラグは変わらない（ADR-0090）ので、ボットであることを連合先と利用者に示すのは `mybot` の既定が担う。

### 8. 振る舞いの既定（行儀）

すべて既定で有効にし、作者が個別に外せる。

- **自分には応答しない**。自分のアカウントからの通知は振り分けない（外せない）。
- **bot フラグのアカウントには応答しない**。送り手の `Account.bot` が真なら、ハンドラを呼ばずに処理済みにする。`RespondToBots: true` で外す。
- **連鎖の上限**: 同じ送り手への返信は 10 分に 5 まで、1 時間に 15 まで。超えた分はハンドラを呼ばずに処理済みにする。bot フラグを立てていない相手のボットとの連鎖も止めるため。
- **公開範囲**: `createStatus` は `visibility` を必須にしていて、サーバーは返信の公開範囲を補わない（`CreateStatusRequest` の `required`。ADR-0017 の「`local` への返信の既定は `local`」はクライアントの既定）。そのため `mybot` が既定を決める。返信の公開範囲は元の投稿より広げない（`direct` には `direct`、`private` には `private`、`local` には `local`、`unlisted` には `unlisted`）。`public` への返信の既定は `unlisted`。
  定期実行の投稿の既定は `unlisted` で、作者が `public`・`local` を明示できる。`local`（ADR-0017）は作者のサーバーの中と作者のフォロワーにだけ届くことを README に書く。
- **返信の宛先**: 返信の本文には元の送り手だけをメンションし、元の投稿の他のメンションを引き継がない（巻き込みを防ぐ）。
- サーバーの規約: ライブラリはサーバーごとの規約を読まない。README に、ボットを動かす前にサーバーの規約（ボットの可否・投稿の頻度）を確かめることを書き、上の既定をその下限の目安とする。

### 9. 実行の形

- ライブラリとして組み込むだけにし、ランナーの CLI・コンテナのイメージは出さない（選択肢 4 は採らない）。
  Go のボットは作者のバイナリになり、TS のボットは作者のスクリプトを `bun`・`node`・`deno` で動かす（対応するランタイムは ADR-0093 に揃える）。例には `Dockerfile` を 1 つ置く。
- `Run(ctx)`（Go）・`bot.run({ signal })`（TS）が止まるまで動く。Go の例は `signal.NotifyContext` で SIGINT・SIGTERM を受ける。
- **グレースフルシャットダウン**: 止める合図で SSE を閉じ、新しい通知を受けるのをやめ、動いているハンドラを猶予（既定 10 秒）まで待ち、`Store` を書き出して戻る。猶予を過ぎたハンドラは取り消し（`context` / `AbortSignal`）、
  処理済みに記録しないので、次の起動で追いつきの対象になる（冪等キーで二重の投稿にはならない）。
- `RunOnce(ctx)`: 追いつきと、時刻を過ぎた定期実行を 1 回ずつ済ませて戻る。cron・Cloud Run jobs などの短命の実行のため。
- 1 つのボットを複数のプロセスで動かすことは想定しない（`Store` の排他はしない）。誤って動かしても、冪等キーで二重の投稿にはならないが、同じ会話の順序は保証しない。

### 10. テスト

- 作者向けに `mybottest`（Go）と `mybot/testing`（TS の subpath export）を出す。
  - 偽のサーバー: HTTP のテストサーバーで、`mybot` が使う操作（`verifyCredentials`・`listNotifications`・`streaming`・`createStatus` と §4 の補助が呼ぶもの）だけを、`api/openapi.yaml` の型で応答する。
  - イベントの注入: `Inject(notification)` で SSE に通知を流し、`Posted()` で投稿を取り出して確かめる。時計を差し替えて定期実行を進められる。
- このリポジトリの中: ライブラリの単体テスト（Go は `httptest`、TS は `bun test`）と、偽のサーバーの応答を spec と照合するテストを、`mykit` と同じ go-task の文脈（ADR-0093 §8 の `tasks/mykit.yml` に `mybot` を足すか、`tasks/mybot.yml` を並べる）で `check:changed` と merge queue に入れる。
  結合テストは `pkg/mybot/integration/` の試験用モジュールで `pkg/testkit` のサーバーを起動し、エコーのボットがメンションに 1 回だけ返すこと（SSE を途中で切って追いつかせる場合と、ハンドラの途中で止めて再起動する場合を含む）を確かめる。

### 11. 例と文書

- 例: エコー（メンションをそのまま返す）・定時の投稿（`Every` と `CatchUp`）・コマンド（`help`・`ping`・`dice`）の 3 つを Go と TS の両方で置く。例はテストで動かす。
- 英語の README（#1031 の方針）を Go と TS のパッケージに置き、トークンの取り方・スコープ・行儀の既定と外し方・`Store` の選び方・グレースフルシャットダウンを書く。

### この決定を見直す条件

- ADR-0090 の登録者自身へのトークンの形（アクセストークンと refresh token の組）が変わる場合: §7 の手順と `Store` の扱いを、そのトークンの形に合わせて直す。
- 通知の一覧を新しい順に読み直す追いつきが、メンションの多いボットで遅い・レート制限に当たる場合: サーバーの `listNotifications` に「この ID より新しいもの」を古い順で返す引数（例: `min_id`）を足す ADR を書き、§3 をそれに置き換える。
- 選択肢 3 のボット向けの webhook がほかの理由（連携サービス・FaaS のボット）でサーバーに入る場合: `mybot` に受け口のモードを足す。

## Consequences（影響）

- 良い影響
  - ボットの作者は取りこぼし・重複・連鎖・公開範囲を気にせず、ハンドラだけを書ける。
  - サーバーに新しい機能・費用が要らない。SSE の接続数の上限（アカウントごとに 8）の中で 1 本だけ使う。
  - 返信と定期実行の投稿は冪等キーで二重にならないので、`Store` を失っても重複の投稿は起きない。
- 悪い影響・トレードオフ
  - 既定の `FileStore` は書き込めるディスクを要る。読み取り専用のコンテナや Cloud Run では、永続のボリュームか自前の `Store`（DB・オブジェクトストレージ）を用意する必要がある。
    refresh token のローテーションを保存しないと次の起動で認証できないので、常駐のボットにも繰り返し起動するボットにも `MemoryStore` は使えない。
  - 新しい順の一覧を読み直す追いつきは、長く止まっていたボットではページを多く読む。
  - 行儀の既定（bot に応答しない・連鎖の上限・`unlisted` の既定）は、意図してボット同士で会話させたい作者には外す手間になる。
  - ホームの新着（`OnStatus`）は切断のあいだの分を取りこぼす。
  - ランナーを出さないので、コードを書かずにボットを動かしたい人には向かない。
  - 2 言語でハンドラの名前・既定の値・テストの道具を揃え続ける手間がある。
- 後続で必要になる作業（issue にする）
  - Go の `pkg/mybot`（イベントループ・追いつき・`Store`・ハンドラ・コマンド・ミドルウェア・定期実行・行儀の既定）
  - TS の `mybot`（同上）
  - テストの道具（`mybottest`・`mybot/testing`）と、リポジトリの結合テスト
  - 例（エコー・定時の投稿・コマンド、Go と TS）と `Dockerfile`、英語の README
  - `mykit` に足りない部分があれば `mykit` の issue（SSE のクライアント、refresh token のローテーションのフック）
  - リリースの仕組み（ADR-0093）に `mybot` を加える
  - `tools/agentkit/context-map.yaml` に `mybot` の領域を足す（ADR-0093 の作業で `pkg/mybot` の領域を足すなら、その中身を埋める）
- 要件（ADR-0093 の FR-504 と並べて `docs/requirements/` に足す）
  - `01-functional.md`「クライアント API」: 「FR-505 | Go と TypeScript（npm）のボット制作ライブラリ `pkg/mybot` を `pkg/mykit` の上に MIT で公開する。通知のイベントのハンドラ・コマンド・定期実行を持ち、切断や再起動のあとも取りこぼさず 2 度応答しない。bot フラグの確認・ボットへの無応答・公開範囲を広げない返信を既定にする（ADR-0094） | S」

## Pros and Cons of the Options（詳細比較・任意）

| 観点 | 1. SSE + 追いつき + Store | 2. ポーリング + マーカー | 3. ボット向け webhook | 4. ランナー中心 |
| --- | --- | --- | --- | --- |
| 取りこぼし・重複 | 追いつき + ID の記録 + 冪等キー | マーカーを人が進めると飛ばす | サーバーの再送（ADR-0060 の仕組み）で強い | 1 と同じ |
| 応答の速さ | 即時 | 間隔ぶん遅れる | 即時 | 即時 |
| サーバーの変更 | なし | なし | 利用者単位の webhook・データモデル・画面・SSRF の考慮が要る | なし |
| ボット側の状態 | `Store`（既定はファイル） | なし | なし（受け口の公開 URL が要る） | 1 と同じ |
| 動かす場所 | どこでも（外向きの接続だけ） | どこでも | 外から届く URL が要る（FaaS には向く） | イメージのある場所 |
| 少ないコード | ハンドラだけ | ハンドラだけ | 受け口の公開と署名の検証が加わる | 設定とスクリプトだけ（最も少ない） |

- 選択肢 2 の最も強い点は、ボットが状態を持たず、どこで再起動しても続きから読めること。マーカーを人の既読と共有する欠点がなければ最も単純で、`Mode: Polling` としては取り入れる。
- 選択肢 3 の最も強い点は、配送の保証をサーバーの再送に任せられ、FaaS（Lambda・Cloud Run）で常駐せずにボットを動かせること。サーバーの機能・費用と SSRF の面が増えるので、v0 では採らない。
- cron の式の解釈: Go の `robfig/cron`（MIT）は使えるが、最後の版が 2020-01 の v3.0.1 で保守が止まっている（2026-10-23 に github.com/robfig/cron で確認）。5 フィールドだけなら自作が小さいので、Go は依存を持たない。TS は保守中の `croner` を使う。
- 選択肢 4 の最も強い点は、コードを書かない人にも開けること。TS のスクリプトを読むランナーは結局ライブラリと同じ API を要し、Go では作者のバイナリになるので、ランナーの形の価値は TS の一部に限られる。
