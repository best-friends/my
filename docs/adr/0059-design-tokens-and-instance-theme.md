# ADR-0059: デザイントークンの体系とサーバー単位のテーマ

- Status: Accepted（生成したトークンの一覧をコミットする範囲を ADR-0081（Go が読む生成物だけをコミットする） が置き換える）
- Date: 2026-10-20
- Deciders: @rosylilly
- Issue: #649

## Context（背景・課題）

決定者の指示は「デザイントークンの管理を強化したうえで、トークン上書きによる独自テーマをサーバーで適用できる仕組み」である。
Web クライアント（FR-601）・管理画面（FR-602）・サーバー単位のテーマ（FR-605）に関わり、実装は #664 が待っている。

トークンは `app/ui/src/theme.css` が Tailwind CSS v4（ADR-0025）の `@theme` で持つ。

- 色は 2 層: `--palette-*`（OKLCH の原色。ユーティリティを作らない）と、`light-dark(<ライト>, <ダーク>)` で原色を指す意味の色 `--color-*`（`@theme static` なので必ず出力される）。
- 色以外（文字・行の高さ・余白の単位・角丸・影・動きの時間と緩急）も同じファイルの `@theme` にあり、Tailwind の既定の値の多くは `initial` で消してある。
- `app/ui/src/tokens.ts` が前景と背景の組と用途（文字 4.5:1、UI 3:1）を列挙し、`make web-tokens`（`app/ui/scripts/check-tokens.ts` と `scripts/color.ts`）が
  両方のテーマで WCAG 2.2 AA のコントラスト、原色の sRGB の色域、組にも装飾の一覧にもない意味の色、既定のパレット・任意の色・`motion-safe:` の外の動きの使用を検査する。
- テーマの切り替えは `<html data-theme>`（ライト / ダーク / なしで OS）だけで、`public/theme.js` が最初の描画の前に付ける（web-client.md §9）。

サーバーごとの見た目の違いは、Web App Manifest と外枠の `theme-color`（`internal/interface/web` の `Options.ThemeColor` / `BackgroundColor`）しかなく、
それも設定から渡す経路がなく既定の `#ffffff` のままである。

制約は次のとおり。

- 外枠の HTML はすべての閲覧者に同じもので、60 秒の共有キャッシュがあり、CSP は nonce のない `style-src 'self'` と Trusted Types である（ADR-0028、ADR-0019 §9、web-client.md §9）。
  部品は `setAttribute('style')` や `cssText` を使わない（D10）。
- サーバーが描画する画面（web-client.md §8）は JavaScript なしで動き、`server-pages.css` で同じトークンを使う。
- 品質ゲート（ADR-0027）は、ライト / ダークの両方でコントラスト AA と axe を求め、`@my/ui` のスクリーンショットを比べる。
- 設定はイベント（リビジョン）と投影に分け、問い合わせや制約のあるデータを JSON に入れない（ADR-0020、data-model.md §4.9）。

## Decision Drivers（判断基準）

1. **管理者による見た目の自由**: サーバーの管理者が、色だけでなく余白・角丸・文字、さらに任意の CSS で見た目を変えられる（決定者の判断）。
2. **CSP とキャッシュを緩めない**: インラインのスタイル・nonce・閲覧者ごとの外枠を足さない（ADR-0028、ADR-0019）。
3. **最初の描画からテーマが当たる**: 既定の見た目が一瞬見えない。JavaScript のないサーバーの画面にも当たる。
4. **トークンの上書きはアクセシビリティを壊さない**: 色のトークンの上書きは、ライト / ダークの両方でコントラスト AA を満たさなければ保存できない（ADR-0027、Y3）。
   任意の CSS の結果は管理者の責任とし、何を保証して何を保証しないかをはっきりさせる。
5. **トークンの定義が 1 か所**: 上書きできるトークンの一覧・既定値・値の形・コントラストの組を、CSS・TypeScript・Go で別々に書かない。
6. **依存を増やさない**: Accepted ADR が決めたライブラリ（Tailwind CSS v4、Storybook 10 など）の範囲で作る。

## Considered Options（選択肢）

### A. トークンの体系（定義の元）

1. **A1: `theme.css` を元のままにし、上書きの対象と検査の組をそこから生成する**。
   Tailwind v4 は CSS を設定の元にする（[Theme variables](https://tailwindcss.com/docs/theme)。テーマの変数は通常の CSS 変数として出力され、ユーティリティもそれを参照する）。
2. **A2: JSON / TypeScript の 1 つの定義から CSS と Go を生成する**（Style Dictionary のような変換の仕組み）。定義を言語に依らない形にできるが、
   Tailwind の `@theme` の書き方（`--color-*: initial`、`static`）を生成器で再現することになり、新しい依存か自作の変換器が要る。

### B. 上書きできる範囲

1. **B1: アクセントの色だけ**（`accent` / `accent-hover` / `accent-fg` / `focus`）。最小で、壊れにくい。
2. **B2: 意味の色（`--color-*`）を、ライトとダークそれぞれに**。
3. **B3: 原色（`--palette-*`）まで**。原色は意味の色の実装の詳細で、名前や段階を変えると上書きが別の色を指すようになる。
4. **B4: 意味の色に加えて、文字・余白・角丸・影なども**。

### C. 検証

1. **C1: 保存のときにサーバー（Go）が、`make web-tokens` と同じ組でコントラストを検査して拒む**。管理画面は同じ計算で入力中に結果を示す。
2. **C2: 管理画面（クライアント）だけで検査する**。API を直接呼べば、AA を満たさないテーマを保存できる。
3. **C3: 検査せず、警告だけにする**（Mastodon のカスタム CSS や Misskey のテーマと同じく、管理者の責任にする）。

### D. 配信

1. **D1: サーバーが同じオリジンのスタイルシートを返し、外枠とサーバーの画面が `<link rel="stylesheet">` で読む**。
2. **D2: `GET /instance` で値を返し、クライアントが起動後に当てる**。最初の描画では既定の見た目が見え、JavaScript のないサーバーの画面には当たらない。
3. **D3: 外枠の `<style>` に埋め込み、CSP に `'sha256-…'` を足す**。テーマの版ごとに CSP が変わり、`style-src` を緩める。

### E. 任意の CSS

1. **E1: 許さない**。トークンの上書きだけにし、品質ゲートの保証を保つ。
2. **E2: 許す**（Mastodon の管理画面の「カスタム CSS」。
   [`CustomCssController`](https://github.com/mastodon/mastodon/blob/main/app/controllers/custom_css_controller.rb) が設定の CSS をそのまま `text/css` で 1 か月の公開キャッシュ付きで返す。
   GoToSocial はアカウントごとのカスタム CSS を既定で無効にし、公開登録のサーバーでは無効のままにするよう[強く勧めている](https://docs.gotosocial.org/en/latest/configuration/accounts/)。
   ここで許すのはサーバーの管理者の CSS だけで、利用者ごとの CSS ではない）。

他のサーバーの仕組み（2026-10-20 に一次資料で確認）:

- **Mastodon**: 任意の CSS を 1 つの設定に持ち、同じオリジンのスタイルシートで配る（E2）。検査はない。
- **Misskey**: テーマは `props` のキーが CSS 変数になる JSON5 で（[テーマの説明](https://misskey-hub.net/en/docs/for-users/features/theme/)）、
  管理者はブランディングの画面で `themeColor` と、サーバーの既定のライト / ダークのテーマ（`defaultLightTheme` / `defaultDarkTheme`）を設定できる
  （[`Meta.ts`](https://github.com/misskey-dev/misskey/blob/develop/packages/backend/src/models/Meta.ts)、
  [`branding.vue`](https://github.com/misskey-dev/misskey/blob/develop/packages/frontend/src/pages/admin/branding.vue)）。変数による上書きは B2 に近いが、コントラストの検査はない。
- **Pleroma / Akkoma**: Pleroma-FE の既定のテーマ名を `frontend_configurations` の `pleroma_fe` に書き、テーマの JSON を静的ファイルとして置く
  （[Theming your instance](https://docs.pleroma.social/backend/configuration/howto_theming_your_instance/)）。設定の変更には再起動が要る。
- **GoToSocial**: 管理者は `web/assets/themes` に CSS のテーマのファイルを置き、再起動する（[Themes](https://docs.gotosocial.org/en/latest/admin/themes/)）。

## Decision（決定）

**A1・B4・C1（色のトークンの上書きに限る）・D1・E2 を採る。** 管理者は `theme.css` のトークン（原色を除く）を上書きでき、さらに任意の CSS を足せる。
サーバーが保証するのは、トークンの上書きの値の形と、色のトークンのコントラストである。任意の CSS の結果は管理者の責任とする。

### 1. トークンの体系の強化

- `theme.css` をトークンの唯一の定義にする（A1）。上書きできるトークンは `@theme`（`inline` でない）に置き、ユーティリティが `var(--*)` を参照する状態を保つ。
  上書きは CSS 変数の値を替えるだけで効く。上書きできるトークンを `@theme inline` にしないことを `theme.css` の注記と検査で守る。
- `app/ui/scripts` に生成器（Bun）を足し、`theme.css` と `tokens.ts` から次を作る。生成物はコミットし、`make web-tokens` が古いと失敗する（`make i18n-gen` と同じ扱い）。
  - Go の `internal/domain/instance` の生成ファイル: 上書きできるトークンの一覧、それぞれの値の種類（色・長さ・フォントファミリー・影・時間・緩急・数）と既定値
    （色はライト / ダークを `#rrggbb` に解決したもの）、コントラストの組と最小値。
    ドメインは標準ライブラリだけで、値の種類ごとの書式の検査と、WCAG 2.2 の相対輝度とコントラスト比（`scripts/color.ts` と同じ式）を計算する。
  - クライアントの `@my/ui` の同じ一覧（管理画面の入力・プレビュー・検査が使う）。`scripts/color.ts` のコントラストの計算は `src` へ移し、検査スクリプトと管理画面が共有する。
- 部品の側では、色以外のトークン（文字・余白・角丸・影・動き）も今の `theme.css` の値と app/ui/README.md の役割の表を正とし、検査を強める:
  `make web-tokens` は、任意の値の角丸・影・動きの時間（`rounded-[3px]`、`shadow-[…]`、`duration-[…]`）と、README にない余白の段階も拒む。
  部品がトークンだけを使うことで、トークンの上書きが画面全体に一様に効く。
- Storybook の `Foundations/Tokens` に、上書きの見本（色と余白・角丸を変えたテーマ）を当てた表示を足す。

### 2. 上書きできる範囲（B4）

- 上書きできるのは、`theme.css` の `@theme` にある原色以外のトークンである。指定しないトークンは既定値のまま。
  - 意味の色 `--color-*`（`overlay`、状態の色 `danger` / `success` / `warning` とその `-fg` を含む）: ライトとダークそれぞれに `#rrggbb`。`overlay` だけは `#rrggbbaa` も受け付ける。
    `#rrggbb` は sRGB の中にあることが書式で決まり、色域の検査が要らず、管理画面の色の入力（`<input type="color">` の値）と同じ形になる。
  - 文字: `--font-sans` / `--font-mono`（フォントファミリーの名前の並び）、`--text-*` の大きさと行の高さ。
  - 余白の単位 `--spacing`、角丸 `--radius-*`、影 `--shadow-*`、動きの時間と緩急。
- 長さと数には、画面が使えなくならない範囲の上限と下限を生成ファイルに持たせる（範囲の値は実装（#664）で決め、app/ui/README.md に書く）。
- 原色（B3）は上書きできない。原色は意味の色の実装の詳細で、名前と段階が版で変わりうるため。原色を替えたいときは、意味の色を直接上書きする。
- ロゴ・ファビコン・PWA のアイコンの差し替えはこの ADR に含めない（画像の扱いは別の Issue で決める）。

### 3. 任意の CSS（E2）

- 管理者はトークンの上書きに加えて、任意の CSS を 1 つ保存できる。長さには上限（実装で決める。例 64 KiB）を設ける。
- 任意の CSS は、トークンの規則の後に `@layer` の外で同じスタイルシートに入るので、部品のスタイルにも勝つ。
- **CSP は緩めない**。任意の CSS も外枠と同じ CSP の下で動くので、別のオリジンの `@import`・画像・フォントは読めない（`style-src` / `img-src` / `font-src` が `'self'`）。
  使えるのは同じオリジンの資源だけで、そのことを管理画面と運用の文書に書く。
- サーバーは CSS の中身を解釈・サニタイズしない。CSS は独立した `text/css`（`X-Content-Type-Options: nosniff`）の応答で返し、HTML に埋め込まないので、HTML の文脈に出ることはない。
  任意の CSS を書けるのはサーバーの管理者（サーバーそのものを運用する者）だけで、利用者ごとの CSS は許さない。
- 任意の CSS が当たるのは、クラス名や DOM の構造に依存する部分である。これらは安定した API ではなく、版の変更で壊れうる。安定して上書きできるのはトークンだけである。

### 4. 検証（C1 の範囲と管理者の責任）

- **サーバーが検証すること**（管理 API の `PUT` が上書きの全体を置き換えるときに、Go のドメインが検査する。満たさなければ保存せず、422 の Problem に理由を並べて返す。ADR-0016）:
  - 上書きのトークンの名前が生成した一覧にあること、値がトークンの種類の書式と範囲に収まること。値は CSS に入るので、書式の検査が注入も防ぐ（`;`・`}`・`url(`・コメントを含む値は書式に合わない）。
  - 色のトークンの上書きを既定値と合わせ、生成した組のすべてをライトとダークで検査し、1 つでも最小値を下回れば拒む（上書きしたトークンが既定のトークンとの組で落ちる場合も含む）。
    #664 の受け入れ基準「コントラストが足りない上書きは保存できない」はこの検査である。
  - 任意の CSS の長さの上限。
- **サーバーが検証しないこと（管理者の責任）**: 任意の CSS が色・余白・表示に与える結果（コントラスト、横スクロール、タップ領域、フォーカスの表示、RTL）。
  管理画面は任意の CSS の欄に、この責任と、品質ゲート（ADR-0027）が既定のテーマに対してだけ働くことを示す。
- 管理画面は同じ一覧と計算で、入力中に色の組ごとの比を示し、下回る組があるうちは保存のボタンの前に理由を示す（保存の判定はサーバーが正）。
- 保存は ADR-0020 に従い、テーマのリビジョン（イベント。任意の CSS の本文を持つ）と、そのリビジョンのトークンの行（トークン・テーマ・値。トークンとテーマは CHECK で限る）と、
  現在のリビジョンの投影に分ける。トークンを JSON の列に入れない。テーブルの形は実装（#664）で data-model.md に書く。
  権限は既存の `manage_settings`（ADR-0058（#648）がモデレーションとサーバー管理を分けるときはサーバー管理の側）、変更は監査ログ（ADR-0037）に残す。

### 5. 配信（D1）

- `my serve` が、現在のテーマを 1 つのスタイルシートにして、リビジョンを含むパス（例 `/theme/{revision}.css`）で返す。中身は次の順である。
  1. トークンの上書きの `:root { … }` の規則。色は `light-dark(#…, #…)` にする。名前は生成した一覧から、値は検査済みのものだけから組み立てる。
  2. 任意の CSS。
  どちらも `@layer` の外に置くので、Tailwind が `@layer theme` に出す既定値と部品のユーティリティに勝つ。
  内容はリビジョンで決まるので `immutable` で長期キャッシュする。上書きも任意の CSS もないときは `<link>` を出さない。
- SPA の外枠と、サーバーが描画する画面は、ビルドのスタイルシートの後に `<link rel="stylesheet">` で読む。スタイルシートは描画を止めるので最初の描画から当たり、`data-theme` と `light-dark()` の仕組みはそのまま効く。
  CSP（`style-src 'self'`）は変えない。外枠は閲覧者ごとに変わらない（インスタンスごとに 1 つ）ので、共有キャッシュも ETag（テーマのリビジョンを足す）もそのまま使える。
  保存から全員の外枠に届くまでは外枠のキャッシュ（最大 60 秒と再検証の 300 秒）の分だけ遅れる。
- Service Worker は `/theme/` のスタイルシートを実行時にキャッシュし（版付きなのでキャッシュ優先）、オフラインの外枠でもテーマが当たる。
- `theme-color`: 外枠は `media="(prefers-color-scheme: light)"` と `dark` の 2 つの `<meta name="theme-color">` に、テーマの `surface` のライト / ダークの値を書く。
  Web App Manifest の `theme_color` / `background_color` はテーマを 1 つしか持てないので、ライトの `surface` にする。`Options.ThemeColor` / `BackgroundColor` の既定値もトークンの既定の `surface` に合わせる。
  `data-theme` で OS と違うテーマを選んだときのブラウザの枠の色は OS の設定に従う（受け入れる制限）。
  任意の CSS で背景を変えても `theme-color` には反映しない（`surface` のトークンだけが元になる）。
- `GET /instance` は、テーマのリビジョンとスタイルシートの URL、トークンの上書きの値（トークン・ライト・ダーク）を返す。管理画面の初期値と、外枠を使わないクライアント（下記の Tauri）のためである。
  管理 API は任意の CSS の本文も返す。

### 6. Tauri のアプリ

- Tauri のアプリ（ADR-0008、FR-603）はビルドした UI を同梱し、接続するサーバーが実行時に変わるので、外枠の `<link>` は使えない。
  サーバーのスタイルシートを取得し、構築できるスタイルシート（`new CSSStyleSheet()` の `replaceSync` と `document.adoptedStyleSheets`）で当てる。
  CSSOM による変更は D10 の禁止（`style` 属性・`cssText`）に当たらない。最初の描画の前に当てるため、前回の内容をアプリの保存領域に残して起動時に先に当てる。
  WebView での動作の検証は Tauri の作業（#31）で行い、急がない。

### 7. テスト

- 品質ゲート（ADR-0027）のスクリーンショット・axe・横スクロールの検査は、既定のテーマに対して行う。
- テーマについての E2E は小さく保つ: 見本のテーマ（色・余白のトークンの上書きと短い任意の CSS）を保存した `my serve` で、外枠とサーバーの画面がスタイルシートを読み、
  トークンと任意の CSS が当たっていることだけを確かめる。
- 管理 API の検査（書式・範囲・コントラスト・長さ）は Go の単体テストで網羅する。

### 既存の ADR との関係

Accepted ADR の決定は置き換えない。ADR-0028 の「外枠を閲覧者ごとに変えない・CSP の nonce を使わない」と ADR-0019 §9 の CSP の範囲で、外枠に同じオリジンのスタイルシートを 1 つ足す。
ADR-0027 の品質ゲートは既定のテーマに対して働き、管理者のテーマについては色のトークンのコントラストだけをサーバーが保証する。

## Consequences（影響）

- 良い影響
  - 管理者はコードを変えずに、色・文字・余白・角丸と任意の CSS でサーバーの見た目を変えられる（FR-605）。
  - 色のトークンの上書きは、どの組み合わせでもライト / ダークの両方で AA が保たれる。
  - CSP・外枠のキャッシュ・JavaScript なしのサーバーの画面がそのまま動き、最初の描画からテーマが当たる。
  - トークンの上書きは名前にだけ依存するので、部品の作り替えで壊れない。
- 悪い影響・トレードオフ
  - 任意の CSS と、文字・余白のトークンの上書きは、コントラスト・横スクロール（D3）・タップ領域（D4）・RTL を壊しうる。サーバーはそれを検査せず、管理者の責任になる。
  - 任意の CSS は部品のクラス名と DOM に依存するので、版を上げると効かなくなったり崩れたりしうる。リリースノートで知らせる以上の互換は約束しない。
  - `app/ui` の変更が Go の生成ファイルを古くする。`scripts/changed-contexts.sh` で `app/ui` の変更が `go-check` も選ぶか、生成物の検査を web 側に置くかを実装で決める。
  - 1 つの色を変えると別の組が落ちることがあり（`accent` を明るくすると `accent-fg` も替える必要がある）、管理画面にそれを分かりやすく示す作業が要る。
  - 外枠のキャッシュの分だけ、保存してから全員に届くまで数分遅れる。
  - ブラウザの枠の色（`theme-color`）は `data-theme` の選択と任意の CSS に追従しない。
- 後続で必要になる作業（Issue 化する）
  - #664: 生成器と生成物の検査、Go のドメインの検査、管理 API と管理画面（トークンと任意の CSS）、スタイルシートの配信、外枠・サーバーの画面・Service Worker・マニフェストの変更、
    小さな E2E、app/ui/README.md と web-client.md（§8・§9・§11・§14）・data-model.md・api/openapi.yaml・運用の文書の更新。
    最初に、`@layer` の外の `:root` の規則によるトークンの上書きが Tailwind v4 のビルドでユーティリティに効くことを確かめる。
  - `make web-tokens` の色以外のトークンの検査の強化と、Storybook の上書きの見本（#664 に含めるか別の Issue にする）。
  - Tauri のアプリでの適用（#31 と Tauri の作業の Issue に含める）。

## Pros and Cons of the Options（詳細比較・任意）

| | 長所 | 短所 |
| --- | --- | --- |
| A1（採用） | Tailwind v4 の書き方のまま、生成器は読むだけ。依存が増えない | CSS を正規表現で読む生成器（今の `check-tokens.ts` と同じ）に依存する |
| A2 | 言語に依らない定義。Go からも直接読める | `@theme` の書き方の再現が要り、新しい依存（ADR が要る）か自作の変換器が増える |
| B1 | 入力が少なく、壊れにくい | 管理者が変えたい余白・背景・文字に足りない |
| B2 | 意味のある単位で色を変えられ、組の検査がそのまま使える | 余白・角丸・文字を変えられない |
| B3 | 原色の段階ごと替えられる | 原色の名前と段階が実装の詳細で、版の変更で上書きの意味が変わる |
| B4（採用） | 見た目を大きく変えられ、トークンの名前だけに依存する | ロケールの行の高さ・横スクロール・タップ領域を上書きのたびに保証できない（範囲の制限と管理者の責任で受ける） |
| C1（採用、色のトークン） | API を直接呼んでも色のトークンの AA が保たれる。クライアントと同じ組 | Go にコントラストの計算と生成物が要る。任意の CSS には効かない |
| C2 | サーバーの実装が少ない | API から不正なテーマを保存できる |
| C3 | 最も自由 | ADR-0027 のゲートを管理者の入力が破れる |
| D1（採用） | CSP・キャッシュを変えず、最初の描画から当たり、JavaScript なしの画面にも当たる | 外枠のキャッシュの分だけ反映が遅れる。リクエストが 1 つ増える |
| D2 | サーバーの変更が少ない | 最初の描画で既定の見た目が見え、サーバーの画面には当たらない |
| D3 | リクエストが増えない | CSP をテーマの版ごとに変え、`style-src` を緩める |
| E1 | 品質ゲートの保証が保たれ、版の変更で崩れない | トークンにない変更（特定の部品の見た目）ができない |
| E2（採用） | 最も自由（Mastodon と同じ）。管理者の求めに応えられる | コントラスト・axe・RTL・スクリーンショットのゲートを保証できず、版の変更でセレクタが壊れうる |

## Open Questions / 要検証

- `@theme static` の意味の色と `@theme` の色以外のトークンを、`@layer` の外の `:root` の規則で上書きするとユーティリティの値が替わることは、#664 の最初に E2E で確かめる
  （要検証。[Theme variables](https://tailwindcss.com/docs/theme) はテーマの変数が通常の CSS 変数として出力されることだけを述べている）。
- Tauri の WebView（WKWebView・Android WebView）で、CSP の下で `adoptedStyleSheets` が使えることは、Tauri の作業（#31）で確かめる（要検証）。
